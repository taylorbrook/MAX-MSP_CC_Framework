object in five places — including telling the user to insert it — but that object is marked
`verified_installed: false` in overrides.json (commit 9ddd8c4) and does not exist in the installed
bach package. A patch built on that advice fails at load with "No such object".

Replace the endorsement with a name-agnostic install-state blocker, strip the dead special-cases,
rewrite the misleading suggestion to name only objects that actually exist, and correct the three
doc sites that steer generation agents toward the same trap.

Purpose: the critic must flag the missing object rather than recommend it.
Output: a generic `verified_installed: false -> blocker` check in the package critic, corrected
Bach guidance in code and docs, and tests proving both directions (flags False, silent on None).
</objective>

<decisions>
- **D-01** — The new check emits severity `blocker` (not `warning`). Rationale: the patch fails to
  load in MAX with "No such object". That is a hard failure, same tier as the existing Bach
  llll-mismatch blocker in the same module.
- **D-02** — The predicate is `db.get_install_state(name) is False`. NOT
  `db.is_verified_installed(name)`, which per D-10 collapses to `state is True` and returns False
  for all ~2,015 unaudited objects — using it would blocker-flag the entire database.
- **D-03** — The check is name-agnostic (reads install state from the DB), so `bach.llll2list` and
  `bach.list2llll` are handled by one identical rule and any future object marked
  `verified_installed: false` is covered automatically.
- **D-04** — The llll-mismatch blocker's suggestion is rewritten from the CLAUDE.md "bach
  (package)" rule: flat MAX lists connect directly to bach inlets; complex conversions use
  `bach.flat` / `bach.iter` / `bach.pack`; element extraction uses `bach.nth N` (1-based,
  `@unwrap 1` when the element is itself a sublist).
- **D-05** — The three doc sites that steer generation agents are in scope
  (`max-patch-agent/SKILL.md`, `max-lifecycle/SKILL.md`, `.claude/max-objects/PACKAGES.md`),
  because leaving them makes agents emit exactly the object the critic now blocks.
- **D-06** — The check lives in `package_critic.py` and is invoked unconditionally from
  `review_packages()` alongside `_check_community_extracted()`. It is NOT moved into
  `structure_critic` — that would change unrelated critic behavior, which this task forbids.
</decisions>
