# Quick Task 260921-i71: Package Critic Install-State Blocker Summary

The package critic now flags objects the database marks as absent from this MAX install instead of recommending one of them as a fix.

## What Changed

`_check_bach_llll_types` treated `bach.list2llll` as a valid, recommended object in five places — including a `suggestion` string telling the user to insert it between a MAX list source and a bach llll inlet. That object is marked `verified_installed: false` in `overrides.json` and does not exist in the installed bach package, so a patch built on that advice failed to load with "No such object".

Three commits:

1. **`d27a6be`** — new `_check_install_state(box_lookup, db)` in `package_critic.py`, called unconditionally from `review_packages()` right after `_check_community_extracted()`. Iterates boxes, resolves names with the module-local `_get_object_name()`, and emits one `blocker` per canonical name whose `db.get_install_state(name)` is `False`. Every object name in the finding and the suggestion is interpolated from the runtime variable — the function contains no hardcoded object name.
2. **`5fd4855`** — deleted all four remaining converter references in `_check_bach_llll_types` (docstring sentence, destination guard, source guard, suggestion) and rewrote the suggestion per D-04: a flat MAX list connects directly to a bach inlet; `bach.flat` / `bach.iter` / `bach.pack` for structured conversion; `bach.nth N` (1-based, `@unwrap 1` for sublist elements) for extraction.
3. **`56e11a0`** — corrected the three doc sites that steered generation agents toward the same trap.

## Key Findings

**Both special-cases were already dead code before removal.** Confirmed empirically at planning time and again here: `bach.list2llll`'s inlet 0 digest is `"Input"` (no "llll"), so `_is_llll_inlet` returned False for it regardless of the destination guard; and as a source it carries `package: "Bach"`, so `src_is_bach` was already True without the source guard. `review_packages()` on the `unpack -> bach.list2llll` fixture returned `[]` before this change. **Removing the special-cases alone changed nothing — the new install-state check is what makes the critic flag the object.** This matters for anyone reading the diff: the deletion is hygiene, the new function is the fix.

**The `get_install_state` vs `is_verified_installed` trap.** `is_verified_installed()` collapses to `state is True` (D-10), so it returns `False` for the ~2,015 objects whose `verified_installed` field is simply absent (unaudited) — including `cycle~` and every bach object other than the two converters. Substituting it here would have emitted a blocker for nearly every object in the database and halted all patch generation. Test 4 (`test_install_state_none_is_silent`) pins the tri-state behavior and asserts `db.get_install_state("bach.score") is None` inline as a fixture sanity check, so it cannot silently rot if that object is audited later.

**Blast radius is exactly two objects today**, re-confirmed after the change: `bach.list2llll` and `bach.llll2list` are the only entries in the whole DB carrying `verified_installed: false`. Zero carry `true`.

## Known Boundary (not a defect — recorded deliberately)

`review_patch()` gates `review_packages()` behind `_has_package_boxes()`. That gate is adequate today because both false-marked objects carry `package: "Bach"`, so the gate always passes for them. **A future core (non-package) object marked `verified_installed: false` would be flagged by a direct `review_packages()` call but missed through the `review_patch()` entry point.** Widening the gate would change unrelated critic behavior, which this task explicitly forbade, so it was left alone. If the Phase 30 audit ever marks a core object false, this gate is the first place to look.

## D-12 Integrity

`validate_patch()` (`src/maxpat/validation.py`) has no critic import and is a separate pipeline from `review_patch()` (`src/maxpat/critics/__init__.py`). The new blocker is additive on the critic channel only; `tests/test_schema_extensions.py` including `test_no_validation_result_emitted` is unchanged and green (47 passed). The `db.lookup()` `UserWarning` remains the single validator-side install-state channel.
