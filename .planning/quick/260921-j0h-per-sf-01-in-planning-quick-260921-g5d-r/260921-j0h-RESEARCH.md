## Summary

Both refpages exist, both are readable, and this repo's own extractor (`.claude/scripts/extract_objects.py::parse_standard_xml`) parses them cleanly — I ran it read-only against both files and have the exact output below. The entries should go in **`max/objects.json`** (core domain, no `package` field), not a `packages/Node for Max/` directory: 11 of 13 patch projects have `config.json` with `"packages": []`, and `get_allowed_packages()` returns `[]` for any config lacking the key, which makes every `packages/`-resident object invisible to `Box()` and re-raises the Rule #1 error this task exists to remove.

**The task's `variable_io` premise does not survive the evidence.** Every source in the bundle says `node.script` has exactly **1 inlet / 2 outlets, fixed**: the refpage declares two `<outlet>` elements, the sole documented argument is a required `symbol` (the script filename, not a count), no outlet-count attribute appears in the refpage or in the `node.script` binary's attribute strings, all 24 `node.script` instances in Cycling '74's own patchers carry `numoutlets: 2`, and the anatomy vignette speaks of "the left outlet" and "the rightmost outlet". The "configurable outlets" phrase in CLAUDE.md traces to this repo's own `add_node_script(..., num_outlets=2)` builder, not to Max. Any `variable_io` rule here would be actively harmful: the only formula that could read arg 0 is `first_arg`, and arg 0 is a filename — `_apply_io_formula` would emit a non-integer-first-arg warning on every use and fall back to the default anyway.

**Primary recommendation:** add both objects to `.claude/max-objects/max/objects.json` with `variable_io: false` and fixed I/O (1 in / 2 out), generated by running the repo extractor on the two refpages and applying four curation deltas; add `rnbo_compatible: false`; bump the CLAUDE.md `max/objects.json` count 471 → 473 in the same commit; rewrite the CLAUDE.md Node-for-Max bullet to state the verified I/O instead of the ban. Record the `num_outlets` mismatch in `add_node_script` as a flagged follow-up rather than changing the builder in this task.

## Common Pitfalls

1. **Adding a `variable_io_rules` entry.** Load-time `ValueError` for an unknown formula; a silent non-integer warning for `first_arg`; a misleading `audit_empty_io()` classification for `fixed:2`. Just set `variable_io: false`.
2. **Landing the entries in `packages/`.** Reintroduces the Rule #1 error for 11 projects, and trips `test_package_objects_have_package_field` unless a `package` field is added.
3. **Shipping the `TEXT_HERE` inlet digest.** Zero precedent in `max/objects.json`; it is the SF-06 placeholder taint leaking into curated data.
4. **Forgetting `rnbo_compatible: false`.** `parse_standard_xml` omits it; only the full `extract_all` pipeline backfills it. `ObjectDatabase` tolerates the absence, but every neighbor has it.
5. **Trusting `node.codebox`'s `objarglist`.** It is a copy of `node.script`'s. The object takes no filename.
6. **Forgetting the CLAUDE.md 471 → 473 bump.** SF-02 corrected this table five commits ago; re-staling it in the very next task is the regression pattern the user flags.
7. **Broad `git add`.** A second instance has uncommitted work in `patches/` (`.active-project.json`, `scala-synth.maxpat`, `gen-eq*.maxpat`, `FDNVerb.maxhelp`). Stage `CLAUDE.md` and `.claude/max-objects/max/objects.json` by path.
8. **Running the Max binary.** Explicitly forbidden and unnecessary — every fact above came from reading XML, JSON, and string tables.
