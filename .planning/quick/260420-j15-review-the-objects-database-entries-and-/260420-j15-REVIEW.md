## Data Quality Findings

### DQ-01 — `wrap~` PD-blocklist entry misleads users of MAX's own `wrap~`
**Severity:** moderate
**Disposition:** obvious-correct-fix
**Where:** `.claude/max-objects/pd-blocklist.json` key `wrap~`
**Evidence:**
- `db.is_pd_object("wrap~")` → `True` (blocklist says `pong~ @mode wrap`)
- `db._objects["wrap~"]` exists — MSP domain, 3 inlets / 1 outlet, digest `"Wrap input to a range within an upper and lower bound"`
- `clip~` has the same "both exist" situation and uses the note `"clip~ exists in MAX too -- verify context"`; `wrap~` does not
**Recommendation:** Change the blocklist entry to match the `clip~` disambiguation pattern: `{"max_equivalent": "wrap~ exists in MAX too -- verify context", "reason": "Both PD and MAX have wrap~ (MAX wrap~ is signal range wrap, PD wrap~ is phase wrap)"}`. Applying.

### DQ-02 — 5 objects with `variable_io: true` have no `variable_io_rules` entry
**Severity:** critical (silent mis-count bug)
**Disposition:** judgment-required for 2, obvious-correct-fix for 3
**Where:** `.claude/max-objects/overrides.json` → `variable_io_rules`; also affects `compute_io_counts` in `src/maxpat/db_lookup.py`
**Evidence:**
Query: objects where `variable_io: true` but no rules entry:
- `routepass` — inline `io_rule.outlet_count = "arg_count_plus_1"` (BAD: formula should be `"arg_count+1"` per `_apply_io_formula` supported list)
- `o.route` (Odot package) — inline `io_rule: None`
- `cycle` (MAX, round-robin router) — inline `io_rule.outlet_count = "first_arg"` ✓
- `combine` (MAX) — inline `io_rule.inlet_count = "arg_count"` ✓
- `router` (MAX) — inline `io_rule.inlet_count = "first_arg"`, `outlet_count = "second_arg"` ✓

`compute_io_counts(name, args)` currently falls back to raw default-array length for all 5, silently ignoring the `variable_io` flag and inline `io_rule`.
**Recommendation:**
- **Obvious-correct:** Lift the inline `io_rule` into `overrides.json:variable_io_rules` for `cycle`, `combine`, and `router` (formulas are already in the supported formula set). Applying.
- **Judgment-required:** `routepass` formula naming mismatch (`arg_count_plus_1` vs supported `arg_count+1`) — user should decide whether to normalize the inline `io_rule` schema across the DB or accept the overrides.json duplicate. Applying the override is obvious-correct but the underlying data inconsistency is a broader cleanup.
- **Judgment-required:** `o.route` has `io_rule: None` — need to consult Odot docs before writing a formula.

### DQ-04 — RNBO-domain entries never carry `rnbo_compatible: true`
**Severity:** cosmetic (but surprising to callers)
**Disposition:** informational — **no action** (resolved via explore-260420)
**Where:** `.claude/max-objects/rnbo/objects.json` — all 560 entries
**Evidence:** `sum(o.get("rnbo_compatible") is True for o in rnbo.values()) == 0`. The RNBO-compat signal for rnbo-domain objects is implicit from being in that file. All 301 cross-domain duplicates between rnbo↔{max,msp,gen} appear as "schema mismatches" purely because of this flag discrepancy.
**Resolution:** The "domain-implies-compatible" rule is **already live in code**. `RNBODatabase._load` (`src/maxpat/rnbo.py:57`) seeds `_compat_objects` with every key from `rnbo/objects.json` before scanning other domains for the `rnbo_compatible=true` flag, so `RNBODatabase.is_rnbo_compatible()` (the sole runtime consumer, used by `rnbo.py:207` and `rnbo_validation.py:138`) already returns `True` for every rnbo-domain entry regardless of the flag. The validation script (`.claude/scripts/validate_db.py:361`) and test gate (`tests/test_rnbo_flag.py:16,37`) both explicitly filter out the rnbo domain before counting flags. No downstream consumer is surprised — the 301 cross-domain "schema mismatches" only appear in audit output comparisons. See `.planning/notes/rnbo_compat_convention.md` for the three-consumers map.
**Recommendation:** No code or data change. Flipping the 560 flags would add noise and erode the self-evident "rnbo file = rnbo-compatible list" property. Explicit documentation was added to preserve the convention for future audits.

### FN-03 — `_apply_io_formula` returns `default` on empty args for `arg_count`/`arg_count+1`
**Severity:** moderate (debatable semantics)
**Disposition:** judgment-required
**Where:** `src/maxpat/db_lookup.py:362-366` (`arg_count`, `arg_count+1` branches)
**Evidence:**
```
if formula == "arg_count":
    return len(args) if args else default
if formula == "arg_count+1":
    return (len(args) + 1) if args else default
```
For `route` (`arg_count+1`, default_outlets=3), calling `compute_io_counts("route", [])` returns `(1, 3)`. But a MAX user who writes `route` with no args gets 1 inlet, 1 outlet (just the unmatched). Empty `args` should return `(1, 0+1) = (1, 1)`, not the `default` 3. **Potential mis-count when the args list is genuinely empty.**
Same issue affects `trigger` (`arg_count`, default_outlets=2): no-arg `trigger` in MAX is 1 in / 2 out (b b), which happens to match the default. But the code path is unprincipled — it returns default rather than applying the formula.
**Recommendation:** Change both branches to always apply the formula (`len(args)` / `len(args)+1`), not fall back to default. Need user decision because some callers may depend on the "no-args → default" behavior. Ticket for follow-up.

### FN-04 — `_apply_io_formula.first_arg` silently returns `default` when the first arg is non-integer
**Severity:** moderate (hides malformed patches)
**Disposition:** judgment-required
**Where:** `src/maxpat/db_lookup.py:368-374`
**Evidence:**
```
if formula == "first_arg":
    if args:
        try:
            return int(args[0])
        except (ValueError, IndexError):
            return default
    return default
```
A user who writes `funnel XYZ` (non-integer first arg) gets the default `(2, 1)` silently. No warning, no distinction between "no args" and "args present but unparseable". A malformed patch passes through without signal.
**Recommendation:** Either warn (UserWarning like `_maybe_warn_empty_io`) or raise (stricter). Judgment-required per user preference.

### FN-05 — `get_outlet_types` type inheritance for expanded outlets assumes homogeneity
**Severity:** moderate (depends on object)
**Disposition:** judgment-required
**Where:** `src/maxpat/db_lookup.py:432-444`
**Evidence:** When `num_outlets > len(db_outlets)`, the function inherits the **last** DB outlet's signal/control type for all expanded outlets. For `trigger` (all outlets control) and `route` (last outlet is unmatched, same type as matched), this is correct. For `pack` (1 outlet, control), expanded to N outlets, inherited result is correctly all-control. **No current variable_io object has mixed outlet types**, so the bug is latent, but any future object with mixed outlets will mis-type the expanded ones.
**Recommendation:** Keep current behavior but add a comment noting the assumption; or introduce an `outlet_type_formula` per-rule. Judgment-required.
