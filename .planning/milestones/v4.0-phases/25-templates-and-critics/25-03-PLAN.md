    Include these templates:

    ### FluCoMa: Real-Time Audio Analysis Chain
    **Use case:** Extract spectral features from live audio for visualization or ML input
    **Chain:** audio source -> fluid.melbands~ (or fluid.mfcc~ or fluid.pitch~) -> fluid.stats -> fluid.normalize -> downstream
    **Connection table:** source outlet/type, dest inlet/type for each step
    **Parameter ranges:** fluid.melbands~ numbands (default 40), fluid.stats numderivs
    **Gotchas:**
    - fluid.melbands~ outputs a list of band energies (NOT signal) from outlet 0
    - fluid.stats accumulates over time -- send "reset" message to clear
    - fluid.normalize needs training data first -- send "fit" before "transform"
    - Real-time FluCoMa objects follow standard MSP gain conventions (+/-1 signal range)

    ### FluCoMa: Offline Buffer Processing Pipeline
    **Use case:** Analyze/decompose pre-recorded audio (corpus analysis, NMF decomposition)
    **Chain:** buffer~ (source) -> fluid.bufnmf (or fluid.bufstats, fluid.bufmelbands) -> [bang on completion] -> fluid.dataset -> fluid.kdtree
    **Gotchas:**
    - All fluid.buf* objects are ASYNC -- they output bang from outlet 0 when done
    - Chain multiple buf* operations using bang -> trigger -> next buf* pattern
    - fluid.bufnmf outputs to destination buffer~ (set via @resynth attribute), not via outlets
    - fluid.dataset stores feature vectors for ML queries; fluid.kdtree enables nearest-neighbor lookup

    ### FluCoMa: ML Classification Pipeline
    **Use case:** Train a classifier on audio features, then classify new audio in real-time
    **Train phase:** fluid.buf* analysis -> fluid.dataset (store features) -> fluid.mlpclassifier (train)
    **Predict phase:** real-time fluid.*~ analysis -> fluid.mlpclassifier (predict) -> result mapping
    **Gotchas:**
    - Training is offline (buf* objects), prediction can be real-time
    - fluid.mlpclassifier needs "train" message before "predict"
    - Send feature lists (not signals) to classifier input

    ### BEAP: Extended Modular Templates
    Reference the existing 5 canonical chains in PACKAGES.md. Add two additional templates:

    **BEAP: FM Synthesis Chain**
    **Chain:** bp.LFOscillator (modulator CV) -> bp.FM (carrier, mod input on inlet 1) -> bp.SVF (optional filter) -> bp.VCA (level) -> bp.Stereo
    **Gotchas:**
    - bp.FM expects modulation as 0-5V CV signal, not audio-rate modulation
    - bp.SVF cutoff controlled via 0-5V CV on inlet 1
    - Always route through bp.VCA before bp.Stereo (gain staging convention)

    **BEAP: Sequenced Pattern**
    **Chain:** bp.Steppr (gate + CV) -> bp.ADSR (envelope from gate) AND bp.Oscillator (pitch from CV) -> bp.VCA (envelope on CV inlet) -> bp.Stereo
    **Gotchas:**
    - bp.Steppr gate outlet (0) triggers bp.ADSR; CV outlet (1) controls pitch
    - bp.ADSR outputs 0-5V envelope -- connect to bp.VCA CV input (inlet 1)
    - bp.Oscillator pitch inlet expects 1V/octave CV from bp.Steppr or bp.Keyboard

    Each template section must include a connection table with columns: #, Source, Outlet, Destination, Inlet, Type (signal/CV/list/bang).

    **Part A: Bach templates in max-patch-agent SKILL.md**

    Add a "## Package Workflow Templates" section to .claude/skills/max-patch-agent/SKILL.md, placed AFTER the existing "## Package Intelligence" section and BEFORE "## Editing Existing Patches". Bach is a control-rate/data package (not DSP), so it belongs in the patch agent, not DSP agent.

    Include these templates:

    ### Bach: llll Construction and Manipulation
    **Use case:** Build nested list structures for algorithmic composition
    **Chain:** data source (message/number) -> bach.list2llll -> bach.join / bach.flat / bach.nth (llll manipulation) -> bach.score or bach.roll
    **Connection table:** #, Source, Outlet, Destination, Inlet, Type
    **Parameter ranges:** bach.join numins (default 2), bach.nth index (1-based)
    **Gotchas:**
    - ALWAYS convert MAX lists to llll via bach.list2llll before feeding ANY bach object
    - bach.llll2list converts back to MAX lists when feeding non-bach objects
    - llll is 1-indexed (not 0-indexed like MAX lists)
    - bach.nth extracts by position; bach.flat removes nesting levels
    - Connecting a standard MAX list outlet directly to a bach llll inlet will silently produce garbage -- the package critic will flag this as a blocker

    ### Bach: Notation Display Workflow
    **Use case:** Display and edit musical notation with bach.score or bach.roll
    **Chain:** bach.score (or bach.roll) <- llll data via inlet 0; message box commands (addchord, delete) via inlet 0
    **Output:** bach.score outlet 0 outputs modified llll; outlet 1 outputs notifications
    **Gotchas:**
    - bach.score accepts both llll data AND messages on inlet 0 (messages like "addchord" are distinct from llll data)
    - To initialize: send the full llll to inlet 0
    - To modify: send command messages ("addchord", "delete", "setpitch") to inlet 0
    - bach.score is a UI object -- it needs presentation mode and adequate display size
    - Pitch representation: MIDI cents (6000 = middle C, 100 cents per semitone)

    ### Bach: Algorithmic Composition Pipeline
    **Use case:** Generate musical material algorithmically and display in notation
    **Chain:** algorithm source (metro + counter / random) -> bach.list2llll -> bach.collect -> bach.quantize -> bach.score
    **Gotchas:**
    - bach.collect accumulates lllls until bang -- send bang to collect then route to quantize
    - bach.quantize snaps pitches/durations to musical grid (needs quantization llll on inlet 1)
    - Output of bach.quantize is an llll ready for bach.score
    - Use bach.iter to iterate over llll elements for processing individual notes
