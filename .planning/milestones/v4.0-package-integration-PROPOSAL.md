# v4.0 Package Integration -- Milestone Proposal

## Milestone Overview

**Name:** v4.0 Package Integration
**Goal:** Integrate MAX packages (bundled + community) into the framework at full parity with core domains -- object DB entries with validation, agent guidance, templates, critics, and install-aware gating.
**Phase numbering:** Phases 20-25 (continuing from existing Phase 19)
**Estimated scope:** 6 phases, ~15-20 plans total

## Phase Breakdown

### Phase 20: DB Schema + Package Field

**Objective:** Add package awareness to the object database so every object knows its source package.

**Scope:**
- Add `"package"` field to ALL existing objects (`null` for core, package name for packages)
- Create `package_info.json` registry with per-package metadata: name, tier, prefix, version, install method, description
- Update `ObjectDatabase` in `db_lookup.py`: add `lookup(name, allowed_packages=)`, `list_packages()`, `get_package_objects(pkg)` methods
- Update `validation.py` to warn when using package object not in project's allowed packages
- Add `package` field to extraction pipeline output
- Split `packages/objects.json` into per-package subdirectories: `packages/beap/objects.json`, `packages/vizzie/objects.json`, etc.

**Requirements:** PKG-01, PKG-02, PKG-03, PKG-04

### Phase 21: Bundled Package Extraction (BEAP + Vizzie)

**Objective:** Extract BEAP and Vizzie abstractions into the object DB using a new abstraction parser.

**Scope:**
- Build new `extract_abstractions.py` for bpatcher-based packages (cannot use XML pipeline)
- Parse help patches + open abstraction `.maxpat` files to extract I/O counts and signal types
- Extract ~172 BEAP modules and ~110 Vizzie modules into per-package DB files
- DB entries use `"maxclass": "bpatcher"` with `"abstraction_file"` field
- Also extract remaining bundled packages not yet in DB (Jitter Geometry, Jitter Tools) via XML pipeline
- Verify extracted data against help patches using existing audit pipeline

**Requirements:** PKG-05, PKG-06, PKG-07, PKG-08

### Phase 22: Package-Gated Generation

**Objective:** Ensure agents never silently use package objects the user hasn't confirmed.

**Scope:**
- Add package selection to project config (`config.json` in project directory)
- Update `/max-new` to prompt user for which packages they want to use
- Update `/max-build` to prompt before generating with package objects if not decided at project creation
- Package selection gates which objects agents can use -- `ObjectDatabase` filtering via `allowed_packages`
- No silent generation with unavailable packages -- always user-confirmed

**Requirements:** PKG-09, PKG-10, PKG-11, PKG-12, PKG-13

### Phase 23: Agent Package Intelligence

**Objective:** Give agents deep knowledge of package-specific patterns, conventions, and workflows.

**Scope:**
- Package-specific guidance sections in all relevant agent SKILL.md files
- BEAP: modular patching patterns, CV signal conventions (0-5V range), bpatcher sizing/layout
- Vizzie: video processing chains, standard interconnection patterns
- FluCoMa: audio analysis workflows, ML pipeline patterns
- Bach: llll data type handling, never mix with standard MAX lists
- CNMAT: OSC workflows, mapping patterns
- Package-specific entries in `relationships.json` (e.g., BEAP `bp.VCA` + `bp.Oscillator`)
- Layout overrides for bpatcher-based packages (BEAP/Vizzie modules are larger than standard objects)

**Requirements:** PKG-14, PKG-15, PKG-16, PKG-17, PKG-18

### Phase 24: Community Package Support

**Objective:** Provide DB presence for community packages even when not locally installed.

**Scope:**
- Stub DB entries for all Tier 2 packages (FluCoMa, CNMAT, Bach, Odot, ml.*, IRCAM Spat)
- Stubs include: name, package, prefix, install instructions, marked `"extracted": false`
- Extraction commands for installed packages: `python extract_objects.py --package flucoma --path <path>`
- When user has package installed, extraction populates full DB entries from XML refpages
- Install guidance surfaced in agent prompts when stub objects are referenced

**Requirements:** PKG-19, PKG-20, PKG-21, PKG-22

### Phase 25: Templates + Critics

**Objective:** Provide starter templates and package-aware validation for common package workflows.

**Scope:**
- Starter templates per package (BEAP modular synth, Vizzie video chain, FluCoMa analysis, Bach notation)
- Package-aware critics: BEAP signal convention validator, Bach llll connection checker
- Template integration with `/max-new` -- project creation can scaffold from package templates

**Requirements:** PKG-23, PKG-24, PKG-25, PKG-26

## Architecture Decisions

### 1. Per-Package DB Files

**Decision:** Use per-package subdirectories (`packages/beap/objects.json`, `packages/vizzie/objects.json`, etc.) rather than a single monolithic packages file.

**Rationale:** Cleaner isolation per package, selective loading (only load packages the project uses), easier to update individual packages without touching others. The current single `packages/objects.json` (87 objects) will be split.

### 2. Bpatcher maxclass for Abstractions

**Decision:** BEAP/Vizzie DB entries use `"maxclass": "bpatcher"` with an `"abstraction_file"` field.

**Rationale:** These are bpatcher abstractions, not compiled externals. Patch generation must use `add_bpatcher()` not `add_box()`. The DB entry must reflect the actual maxclass used in .maxpat files.

### 3. ObjectDatabase Load Order Unchanged

**Decision:** Package objects continue to load early in the domain load order. Core domains load last and shadow duplicates.

**Rationale:** The existing load order (`rnbo, packages, m4l, gen, mc, jitter, msp, max`) correctly gives core objects priority. Per-package files load within the `packages` slot.

### 4. Dual Extraction Pipelines

**Decision:** Extend existing `extract_objects.py` for XML-bearing packages; build new `extract_abstractions.py` for bpatcher packages.

**Rationale:** The XML pipeline is proven and handles compiled externals well. BEAP/Vizzie have zero XML refpages -- they need a fundamentally different approach (parsing .maxpat files for inlet/outlet objects). Two tools, each doing one thing well.

### 5. Stub Entries for Uninstalled Packages

**Decision:** Community packages get stub DB entries when not installed, with `"extracted": false` flag. Full entries populated when user runs extraction on installed packages.

**Rationale:** Agents need to know these packages exist so they can mention them when relevant (e.g., "FluCoMa's fluid.hpss~ would be ideal here but requires installation"). Warn-only behavior, never block.

## Risks

| Risk | Severity | Likelihood | Mitigation |
|------|----------|------------|------------|
| Abstraction I/O type detection (signal vs control) requires parsing inner .maxpat files -- more complex than XML extraction | Medium | High | Proof of concept already verified for 90/172 BEAP modules; fallback: open .maxpat directly |
| Bach is very large (~250+ objects) and may need special handling | Low | Medium | Treat as incremental extraction; if too large, split into sub-packages |
| IRCAM Spat requires paid license -- cannot be tested without subscription | Low | Certain | Stub entries only; extraction command provided for licensed users |
| Community package XML format may vary from Cycling'74 standard | Medium | Medium | Test with FluCoMa first (most popular); add format adapters if needed |
| BEAP signal conventions (0-5V CV) need verification from actual BEAP documentation | Low | Medium | Document as assumed; verify when BEAP modules are extracted and tested |

## Open Questions

1. **How to handle abstraction I/O types (signal vs control)?**
   - bpatcher boxes in help patches show `numinlets`/`numoutlets` but not signal vs control
   - Need to open the actual `.maxpat` abstraction and scan for `inlet`/`outlet` objects with signal connections
   - Feasible but requires deeper parsing

2. **Should stub entries for uninstalled packages block or warn?**
   - Recommendation: Warn-only. Agent explains the package isn't installed and offers alternatives.

3. **Additional community packages beyond the named ones?**
   - Claude's discretion per CONTEXT.md. Candidates: Pattrstorage-related packages, MI (Mutable Instruments) ports, karma~ (looper), LowkeyNW.
   - Recommendation: Start with the 6 named packages; add more based on user request.
